# reverse_bot

Оценка **стойкости бинаря к реверс-инжинирингу** и отслеживание регрессий
защищённости между версиями. Бинари — **Raspberry Pi OS (ARM)**.

Ансамбль LLM (Claude, Gemini, Qwen, Grok, ...) атакует бинарь в изолированной
песочнице, пытаясь вскрыть его защиту — зашитые константы и проприетарный
алгоритм. Затем модель-судья, имея на руках исходник-эталон, оценивает, насколько
глубоко удалось вскрыть каждую цель и какой ценой. Балл стойкости сравнивается
между версиями бинаря: упал балл — регрессия защищённости.

Цель не в сравнении моделей между собой: много атакующих нужны, чтобы шире вести
атаку. Цель считается вскрытой, если её взяла **хоть одна** модель.

### Граница доверия

Внутри системы две изоляции, не одна:

1. **Недоверенный бинарь** заперт в контейнере (`--network none`) — не достанет
   ни сеть, ни ключи, ни хост.
2. **Исходник-эталон** (`targets.yaml` + код) виден **только судье** и никогда не
   попадает в песочницу к атакующим. Иначе они «вскроют» защиту, прочитав ответы,
   и замер обнулится. `orchestrate.py` принципиально не знает про исходник —
   в контейнеры уходит только бинарь.

## Подготовка данных (не в git)

`samples/` и `truth/` в репозиторий не входят (`.gitignore`) — там анализируемые
бинари, защищаемый исходник и эталонные ответы. На новой машине их кладут вручную:

```
samples/                      # анализируемое (бинари, IP) — не в git
├── <бинарь>                  #   сам образец для атаки
└── <зависимости>             #   .so, данные модели и т.п., нужные ему для запуска

truth/                        # эталон — виден только judge.py, не в git
├── <исходники>               #   защищаемый код с маркерами @re-target-*
├── Cargo.toml                #   (если Rust) — источник name/version бинаря
└── protected.yaml            #   генерируется из маркеров, НЕ редактируется руками
```

Имена моделей — в нотации LiteLLM; точные строки для OpenRouter см.
[openrouter.ai/models](https://openrouter.ai/models) (меняются со временем).

## В один запуск

```bash
python run_RE.py        # или двойной клик по run_RE.cmd на Windows
```

Прогоняет всю цепочку: `targets_gen.py` → `orchestrate.py` → `judge.py`.
Аргументы атаки (бинарь, зависимости, модели, бюджет, версия) лежат в
`RE_args.txt` рядом со скриптом — правишь его, не команду. Имя прогона скрипт
задаёт сам, поэтому судья находит отчёт без ручного указания пути.

Ключи: `--skip-targets` (не пересобирать `targets.yaml`), `--judge <модель>`,
`--args <файл>` (другой файл аргументов). Отдельные шаги по-прежнему можно
запускать вручную — см. ниже.

## Полный цикл оценки стойкости (вручную)

```bash
# 0. Сборка целей из маркеров в коде (детерминированно, без LLM)
python targets_gen.py --source truth --out truth/protected.yaml --cargo truth/Cargo.toml

# 1. Атака: ансамбль моделей вскрывает бинарь (эталон им недоступен)
python orchestrate.py --sample samples/kerbside \
    --deps samples/libonnxruntime.so samples/vehicle.onnx \
    --models openrouter/anthropic/claude-opus-4.5,<второй-id-из-каталога> \
    --budget-total 6 --label "kerbside-0.1.0"

# 2. Оценка: судья сверяет отчёты атакующих с исходником-эталоном
python judge.py --run ens_<дата> --targets truth/protected.yaml --source truth
```

Бинарь идёт `--sample`, а нужные ему библиотеки и данные — `--deps` (копируются
в песочницу с исходными именами; для запуска `.so` нужен `LD_LIBRARY_PATH=/work`).

Результат — `runs/<прогон>/resilience.json`: балл стойкости (1.0 = ничего не
вскрыто, 0.0 = вскрыто всё), вердикт по каждой цели, и — если есть замер прошлой
версии того же бинаря — дельта. Падение балла = **регрессия защищённости**.

### Эталон в `truth/`

Исходник и `targets.yaml` кладутся в `truth/` (в git не попадает, см. `.gitignore`).
`judge.py` при старте проверяет, что `--targets` и `--source` лежат **вне**
`runs/`, и отказывается работать иначе — эталон не должен оказаться там, откуда
монтируется в контейнеры.

### Разметка защищаемого маркерами

Чтобы не синхронизировать `targets.yaml` вручную, защищаемое помечается одним
коротким маркером прямо в коде (язык неважен — маркер ищется как подстрока):

```rust
// @re-binary: name=protected version=1.4.0

// @re-target-const
const LICENSE_KEY: u32 = 0x4F2A9C31;

// @re-target-algo
//   role: модифицированный XTEA
//   reveal: опознан XTEA
//   reveal: восстановлена дельта
fn cipher_block(..) { .. }
```

`targets_gen.py` собирает `targets.yaml`: `id` = имя константы/функции, значение
и границы тела извлекаются из кода, `weight` по умолчанию `high`. Всё остальное
скрипт подтягивает сам при каждом запуске — номера строк не ведутся вручную.

- Вес: `// @re-target-const low` (иначе high).
- `role:` / `reveal:` — необязательные строки-комментарии под маркером.
- Тело алгоритма определяется по балансу `{}`; для языков без скобок (Python)
  поставьте `# @re-target-end` после тела.
- Метаданные бинаря: `// @re-binary: name=.. version=..`, либо `--cargo Cargo.toml`.

Голое десятичное значение автопарсер берёт только после `=`; если не распозналось,
укажите `value=42` в маркере. `--check` показывает diff и проблемы без записи.
Полная схема — в шапке `targets_gen.py`.

**Компромисс:** `id` цели = имя в коде. Переименование защищаемого меняет `id`, и
`judge.py` увидит это как «цель убрана + новая добавлена» — цепочка регрессии по
ней прервётся. Если код переименуют, а сравнение версий должно продолжаться,
закрепите `id` явно: `// @re-target-const id=license_key`.

## Устройство

```
agent.py (на хосте: есть интернет и API-ключи)
   ├── HTTP ────────────▶ API модели (Claude / Gemini / Qwen / ...)
   └── docker exec ─────▶ контейнер re-workbench
                          сети нет, на запись только /work,
                          внутри Ghidra, radare2, qemu-user, angr, ...
```

Разделение принципиальное: анализируемый код исполняется в контейнере без сети и
без доступа к ключам, а наружу в API ходит только процесс-обвязка на хосте.

## Что в образе

- **Ghidra 12.1.3** + PyGhidra — декомпиляция ARM/AArch64.
- **radare2**, binutils (в т.ч. кросс: `aarch64-linux-gnu-*`, `arm-linux-gnueabihf-*`),
  `gdb-multiarch`, `yara`, `binwalk`, `upx`, `dpkg-deb`.
- **qemu-user-static** + ARM-корни (`arm64` и `armhf`) для запуска и отладки
  ARM-бинарей на x86-хосте. Корни собираются скачиванием `.deb` нужной
  архитектуры и распаковкой через `dpkg-deb` — при сборке не исполняется ни один
  ARM-бинарь, поэтому **binfmt/QEMU на хосте настраивать не нужно**.
- Python: `pyelftools`, `capstone`, `lief`, `r2pipe`; по возможности `angr`,
  `unicorn`, `qiling`, `capa`, `pwntools`, `frida-tools`.
- `/opt/re/TOOLS.md` — шпаргалка, которая подставляется модели в промпт.

## Сборка

```powershell
.\build.ps1
```

Первая сборка — 15–30 минут, в основном Ghidra (~400 МБ) и python-пакеты.
Для Pi OS 2023–2024 берите `-Suite bookworm`.

По завершении автоматически прогоняется `selftest.sh`: он печатает, что
установилось, а что нет. Часть пакетов помечена в `Dockerfile` как необязательная
и может отсутствовать — это не ломает образ, но `selftest` покажет, чего лишились.

### Кодировки при правке файлов

Две несовместимые требования, о которые легко споткнуться на Windows:

- `build.ps1` — UTF-8 **с BOM**. Без BOM Windows PowerShell 5.1 читает файл как
  cp1251, русская «т» (UTF-8 `D1 82`) превращается в `U+201A`, и парсер видит
  открывающую кавычку: `The string is missing the terminator`.
- Всё в `image/` — UTF-8 **без BOM** и **только LF**. Это уезжает в Linux-контейнер:
  BOM ломает `#!/bin/bash`, CRLF даёт `bad interpreter: /bin/bash^M`.

Если редактор или git normalize перевели `image/` в CRLF — образ соберётся, но
обёртки внутри работать не будут.

## Запуск агента

```powershell
pip install -r requirements.txt
copy .env.example .env      # и вписать ключи
python agent.py --sample samples\myapp --model anthropic/claude-opus-4-5
```

Полезные ключи: `--task` (своя формулировка задачи), `--max-turns`, `--max-usd`,
`--keep-container` (не удалять контейнер после работы — удобно для разбора полётов).

При ограничении частоты запросов (частая история на бесплатных моделях) агент
ждёт и повторяет: `--max-retries` (по умолчанию 4) и `--retry-delay` (20 с,
дальше удваивается). Если стоимость модели неизвестна LiteLLM, `--max-usd` не
сработает — скрипт об этом предупредит, а в `summary.json` будет
`"usd": "неизвестно"`.

### Сколько это стоит

Агентный цикл дорог по своей природе: API не хранит состояние, поэтому каждый
шаг пересылает всю прошлую переписку заново. На 16 шагов это ~194 000 входных
токенов, из которых **~90% — повторы одного и того же префикса**.

Лечится кэшированием промпта: помеченный `cache_control` префикс читается по 0.1
обычной цены. Включено по умолчанию, отключается `--no-cache`. Замеры на Opus,
разбор `grep` (200 КБ):

| | без кэша | с кэшем |
|---|---|---|
| Цена шага | $0.129 | **$0.0215** |
| Попаданий в кэш | 0% | **77%** |

`summary.json` показывает `tokens` и `cache_hit_rate` — если доля попаданий
близка к нулю, кэш не работает (сменилась модель, поехал системный промпт).

Что ещё влияет на счёт:

- **Модель.** Sonnet — $2/$10 за миллион токенов против $5/$25 у Opus. Для
  большей части шагов разницы в качестве не видно.
- **Наценка OpenRouter** (~5%) поверх цен провайдера.
- **Обрезка вывода команд** — `MAX_OUTPUT_CHARS` в `agent.py`, сейчас 20 000
  символов. Каждый вывод остаётся в контексте навсегда.

Отдельно: подписка на Claude Code — это тариф с лимитами, а не счётчик. Сравнивать
её «долю пятичасового окна» с суммой по API некорректно: внутри лимита предельная
стоимость нулевая, а API считает каждый токен по прайсу.

Чтобы обрыв по лимиту не уничтожал работу, при достижении `--wrap-at` (75%
бюджета или шагов) агент просит модель немедленно записать выводы через
`re-note` и написать `report.md`. Оставшейся четверти на это хватает. Если
отчёта всё равно нет, рассуждения модели сохраняются в `unfinished_notes.md`.

Результат ложится в `runs/<дата>/<модель>/`:

```
sample           копия образца, с которой работала модель
session.md       читаемый лог: команды и их вывод
transcript.jsonl полный диалог машинно-читаемо
findings.jsonl   находки, записанные через re-note
report.md        итоговый отчёт модели
summary.json     шаги, время, стоимость, причина остановки
```

Имена моделей — в нотации LiteLLM: `anthropic/claude-opus-4-5`,
`gemini/gemini-2.5-pro`, либо через OpenRouter одним ключом:
`openrouter/x-ai/grok-4`, `openrouter/qwen/qwen3-max`.

## Настоящая Raspberry Pi (необязательно)

Эмуляция не умеет GPIO, I2C, VideoCore и библиотеки Pi OS. Если под рукой есть
живая Pi, модель может запускать образец на ней.

Заполните в `.env` блок `RE_PI_*` и проверьте связь:

```bash
python agent.py --check-pi
```

Тогда у модели появляются три инструмента: `pi_push` (закинуть файл),
`pi_exec` (выполнить команду), `pi_pull` (забрать результат). Если `RE_PI_HOST`
пуст, модель о них не узнаёт вовсе. Разово отключить при настроенной Pi —
`--no-pi`.

**Почему не SSH прямо из контейнера.** Контейнер запускается с `--network none`,
и это несущая конструкция всей изоляции: у образца нет сети, а значит нет и
доступа к вашим API-ключам. Поэтому SSH выполняет `agent.py` с хоста, а учётные
данные Pi в контейнер не попадают вообще.

**Риск.** Живая Pi — это реальное железо в вашей сети, и запуск на ней
недоверенного кода даёт ему сеть, диск и возможность закрепиться. Отдельный
сегмент сети, одноразовая SD-карта, уникальные пароли. После сеанса с
недоверенным образцом машину считайте скомпрометированной и перезаливайте.

## Ручной прогон

```powershell
mkdir runs\manual
copy <ваш_бинарь> runs\manual\sample
docker run --rm -it --network none -v "${PWD}\runs\manual:/work" re-workbench:latest
```

Внутри:

```bash
re-help                          # шпаргалка по среде
rpi-info /work/sample            # что за файл, архитектура, зависимости
ghidra-analyze /work/sample      # долгий анализ, один раз
ghidra-funcs -s size -n 40       # крупнейшие функции
rg 'system|popen|/etc/' /work/sample.ghidra/decomp/
ghidra-decompile 0x00012a40
ghidra-xrefs main
rpi-run --strace /work/sample    # запуск под эмуляцией
```

Пройдите этот путь руками хотя бы раз: всё, что покажется неудобным вам, окажется
непреодолимым для модели.

## Ограничения, о которых надо знать заранее

- ARM-корень собран из **чистого Debian**, а не из настоящей Raspberry Pi OS.
  Бинарь, которому нужны `/dev/gpiomem`, VideoCore или `libwiringPi`, под qemu не
  поедет. Лечится подсовыванием настоящего корня из образа Pi OS через
  `rpi-run --root /path/to/rootfs` — или анализом на живой Raspberry Pi.
- `capa` почти бесполезна на ARM-ELF: её правила написаны под x86/Windows.
- Контейнер — не полноценная изоляция от вредоносного кода. Для заведомо
  недоверенных образцов запускайте всё это внутри одноразовой ВМ со снапшотом.
